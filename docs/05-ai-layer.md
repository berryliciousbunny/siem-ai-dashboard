## Overview

The AI layer is a Python FastAPI microservice that sits between the Wazuh Indexer and the SOC dashboard. Every alert generated by Wazuh passes through a staged pipeline before reaching the analyst: anomaly scoring, behavioural analysis, sanitization, and finally a plain-English explanation generated by a language model — local by default, cloud as an opt-in upgrade. The pipeline's output is enrichment and explanation only; it does not decide what automated actions fire. That decision belongs to the policy layer described in [`02-architecture.md`](02-architecture.md), which is deliberately kept separate from anything the AI produces.

---

## Why AI on Top of Wazuh

Wazuh's rule engine is powerful but fundamentally reactive — it matches known patterns against a fixed ruleset. This works well for well-understood attack signatures but has structural limits that AI is well-positioned to address:

| Limitation of rules alone | How the AI layer addresses it |
|---|---|
| Only catches known attack patterns | Anomaly detection flags unknown/novel behaviour by learning what normal looks like |
| All alerts carry one severity number | The anomaly score gives analysts a second, independent signal to prioritise by — shown alongside severity, not blended into it |
| Rules don't adapt to your environment | UEBA builds a per-user baseline specific to your organisation — not generic thresholds |
| Alerts require manual interpretation | An LLM generates a plain-English explanation so L1 analysts don't need to decode every rule ID and log entry |
| No context across alert history | UEBA correlates current behaviour against a rolling history per user |

The AI layer doesn't replace Wazuh's detection engine, and it doesn't replace the response layer either — it sits between the two, adding context that a human (or a fixed policy rule) then acts on.

---

## Design Principles for This Layer

These follow directly from the system-wide principles in `02-architecture.md`, applied specifically to how this microservice is built:

**Telemetry stays local by default.** The default LLM provider is a self-hosted model via Ollama. Nothing about SIEM alert content leaves the machine/network unless the operator explicitly switches `LLM_PROVIDER` to a cloud option.

**Nothing unsanitized reaches a model.** Every alert is passed through `sanitizer.py` before it is turned into a prompt — regardless of which provider is configured. This isn't a cloud-only safeguard; the local model gets sanitized input too, because the point is data hygiene and predictable prompts, not just network boundaries.

**The output is an explanation, not a command.** `summarizer.py`'s return value is stored as `llm_explanation` on the enriched alert. No code path in this service calls TheHive, Shuffle, or an active-response script based on what the LLM said. Those integrations are wired to fixed thresholds on Wazuh severity and rule IDs, which live in the policy layer, not in this pipeline.

**Distinct signals stay distinct.** `anomaly.py` produces an **Anomaly Score** — never referred to as severity anywhere in this codebase or its docs. `ueba.py` produces a **UEBA deviation** with a reason string. VirusTotal produces a **reputation** result. All four are written as separate fields on the enriched alert.

## Pipeline Architecture

Every new alert from OpenSearch passes through five stages in strict order:

```
OpenSearch (wazuh-alerts-*)
        │
        │  FastAPI poller checks every 30 seconds
        ▼
┌───────────────────────────────────────────┐
│           main.py — Alert Retrieval       │
│  Fetches new alerts from OpenSearch       │
└───────────────────┬───────────────────────┘
                    ▼
┌───────────────────────────────────────────┐
│      anomaly.py — Anomaly Detection       │
│  Isolation Forest model                   │
│  Output: anomaly_score (0.00–1.00)        │
└───────────────────┬───────────────────────┘
                    ▼
┌───────────────────────────────────────────┐
│         ueba.py — Behaviour Baseline      │
│  Output: ueba_deviation + reason          │
└───────────────────┬───────────────────────┘
                    ▼
┌───────────────────────────────────────────┐
│      sanitizer.py — Data Sanitization     │
│  Strips secrets, unnecessary PII          │
│  Validates and normalizes remaining       │
│  fields — runs for every provider,        │
│  local or cloud                           │
└───────────────────┬───────────────────────┘
                    ▼
┌───────────────────────────────────────────┐
│      summarizer.py — LLM Gateway          │
│  Builds the prompt from sanitized input   │
│  Routes to configured provider            │
│  Validates the returned explanation       │
│  Also triggers VirusTotal lookup          │
└───────────────────┬───────────────────────┘
                    ▼
        OpenSearch (wazuh-ai-enriched-*)
        Dashboard reads enriched alerts,
        shows all signals separately
```

## Stage Breakdown

---

### `main.py` — Alert Retrieval

**What it does:**
Entry point for the microservice. Runs a background polling loop checking OpenSearch every 30 seconds for new alerts in `wazuh-alerts-*`. For each new alert it runs the full pipeline and writes the result to `wazuh-ai-enriched-*`. Also exposes the REST API endpoints in [API Reference](#api-reference).

```python
# Simplified polling loop
while True:
    new_alerts = opensearch.get_new_alerts(since=last_checked)
    for alert in new_alerts:
        alert["anomaly_score"] = anomaly.score(alert)
        alert["ueba"] = ueba.check(alert)
        sanitized = sanitizer.clean(alert)
        alert["llm_explanation"] = summarizer.explain(sanitized)
        opensearch.write_enriched(alert)
    last_checked = now()
    time.sleep(30)
```

Note that `sanitizer.clean()` runs on every alert before `summarizer.explain()` is ever called — there is no path that skips sanitization, even for the local provider.

---

### `anomaly.py` — Anomaly Detection

**What it does:**
Scores each incoming alert with an **Anomaly Score** from 0.00 to 1.00, where scores closer to 1.0 indicate higher statistical unusualness relative to the learned baseline. This field is always labelled `anomaly_score` — it is a distinct signal from Wazuh's own rule-based severity, and the two are never combined into one number anywhere in this pipeline or on the dashboard.

**How it works:**
Isolation Forest is an unsupervised algorithm that detects anomalies by measuring how quickly a data point can be isolated from the rest of the dataset using random decision trees. Normal points blend in and take many splits to isolate; anomalous points get isolated in very few splits.

```
Normal alert (login at 9am from known IP)
  → Takes 47 random splits to isolate
  → Anomaly Score: 0.12

Anomalous alert (login at 3am from Tor exit node)
  → Isolated in 3 random splits
  → Anomaly Score: 0.94
```

**Training data:** 30 days of historical Wazuh alerts representing baseline activity. No labelled attack data required.

**Features used:**
```python
features = [
    "hour_of_day", "day_of_week", "source_ip_is_known",
    "wazuh_severity", "rule_id", "bytes_transferred",
    "login_failure_count", "is_new_device", "dest_port",
    "alert_count_last_1h"
]
```

Note `wazuh_severity` is used as one *input feature* to the model — that's different from calling the model's output "severity." The output is always `anomaly_score`.

**Score interpretation:**

| Score | Interpretation |
|---|---|
| 0.00–0.30 | Consistent with baseline |
| 0.31–0.60 | Mildly anomalous |
| 0.61–0.80 | Significantly anomalous |
| 0.81–1.00 | Highly anomalous |

This interpretation is advisory for the analyst reading the dashboard — it does not by itself trigger anything in the response layer.

---

### `ueba.py` — User & Entity Behaviour Analytics

**What it does:**
Builds a rolling behavioural profile per user and flags alerts where current behaviour deviates from that baseline. Appends `ueba_deviation` (true/false) and `ueba_reason` (human-readable string) — kept as a field distinct from `anomaly_score`.

**Behavioural dimensions tracked per user:**

| Dimension | Baseline metric | Flag condition |
|---|---|---|
| Login time | Mean hour + std dev | > 2 std devs outside normal window |
| Source IP | Known IP list | Any login from unseen IP |
| Device | Known device list | Any login from unseen device |
| Daily data volume | Mean bytes/day | > 3x daily average |
| Alert frequency | Mean alerts/day | > 5x daily average |

**Why per-user rather than global thresholds:** a global rule like "flag logins after 7pm" false-positives on night shift workers and different time zones. UEBA avoids this by comparing each user only against their own history.

---

### `sanitizer.py` — Data Sanitization

**What it does:**
Sits between the statistical stages and the LLM Gateway. Every alert — regardless of destination provider — passes through this stage before it can be turned into a prompt.

**Responsibilities:**
- Strips fields that are secrets or internal-only (raw credentials if ever present in log payloads, internal hostnames not needed for the explanation, API keys accidentally logged upstream)
- Removes unnecessary PII beyond what's needed to explain the alert (e.g. trims a full user directory record down to just the username)
- Validates field types and normalizes formats (timestamps, IPs) so the prompt template downstream is predictable
- Rejects or flags alerts that fail validation, rather than silently forwarding malformed data to the model

```python
def clean(alert: dict) -> dict:
    sanitized = {
        "rule_id": alert["rule_id"],
        "rule_description": alert["rule_description"],
        "source_ip": alert["source_ip"],
        "destination_host": alert["destination_host"],
        "timestamp": normalize_timestamp(alert["timestamp"]),
        "anomaly_score": alert["anomaly_score"],
        "ueba_deviation": alert["ueba"]["deviation"],
        "ueba_reason": alert["ueba"]["reason"],
    }
    # explicitly does NOT forward: raw log payloads, credentials,
    # internal-only metadata, full user directory records
    return sanitized
```

**Why this stage exists even for the local provider:** sanitization isn't only about keeping data off a third party's servers — it also keeps prompts small, predictable, and free of fields that could confuse or destabilise the explanation the model produces.

## Signal Model

Rather than blending everything into one number, the enriched alert carries four independent signals. The dashboard shows all four side by side:

```
Wazuh Severity     — rule-based, from the Manager's rule engine
Anomaly Score      — statistical unusualness, from anomaly.py
UEBA Deviation     — behavioural deviation, from ueba.py
VT Reputation      — external threat intel, from VirusTotal
```

Example of how one alert's enriched record looks:

```json
{
  "rule_id": 100001,
  "wazuh_severity": 12,
  "anomaly_score": 0.91,
  "ueba_deviation": true,
  "ueba_reason": "Source IP not seen before, activity outside baseline hours",
  "vt_reputation": "47/72 engines flagged",
  "llm_explanation": "..."
}
```

None of these four fields is derived from another — each is computed independently and an analyst can disagree with, or weight differently, any one of them.

## LLM Gateway and Providers

### `summarizer.py` — the gateway

**What it does:**
Takes the sanitized alert, builds a prompt, sends it to whichever provider is configured, validates the response, and returns it as `llm_explanation`. This is the only file in the pipeline that talks to a language model — keeping that logic in one place is what makes switching providers a config change rather than a code change.

```python
def explain(sanitized_alert: dict) -> str:
    prompt = build_prompt(sanitized_alert)
    provider = get_configured_provider()   # local by default
    raw_response = provider.complete(prompt)
    return validate_output(raw_response)
```

**Prompt template:**
```
You are a SOC analyst assistant. Summarise the following sanitized
security alert in 3–5 sentences for a junior L1 analyst. State what
happened, why it looks suspicious given the anomaly score and UEBA
context, which system is affected, and what the analyst should
consider next. This is an explanation for a human to read — you are
not authorized to take or recommend an automatic action; only
describe what you observe.

Alert data:
{sanitized_alert_json}
```

That last instruction in the prompt is deliberate — it reinforces, even at the model level, that the output is descriptive rather than a command, matching the system-wide principle that the LLM never drives the response layer directly.

**Example output:**
```
⚠️ Brute Force Pattern — Anomaly Score 0.91

47 failed SSH login attempts were made against PROD-DB-01 from an
IP address not previously seen in this environment, at a time
outside this user's normal activity window. Wazuh's rule engine
flagged this at severity 12; the anomaly and behavioural signals
both agree this is unusual. Consider confirming whether any
successful login followed from this source before closing this
alert. MITRE: T1110.
```

### Providers

```env
# Local (default) — nothing leaves the network
LLM_PROVIDER=ollama
OLLAMA_MODEL=mistral
OLLAMA_URL=http://localhost:11434

# Cloud (opt-in upgrade path)
LLM_PROVIDER=anthropic
ANTHROPIC_API_KEY=your_key_here

LLM_PROVIDER=openai
OPENAI_API_KEY=your_key_here

# Disabled — structured text summary only, no model call at all
LLM_PROVIDER=none
```

Switching providers only changes which `provider.complete()` implementation `summarizer.py` calls — sanitization, prompt construction, and output validation are identical regardless of provider.

## Limitations, Root Causes & Improvement Path

---

### 1. Cold Start Problem (UEBA)

**What it is:** UEBA needs 30–60 days of history before per-user baselines are meaningful. Early on, deviation flags are unreliable.

**Why it exists:** Statistical baselines need enough data points for a reliable mean and standard deviation.

**How to navigate it now:** Weight UEBA flags lower in the first 30 days; rely more on Wazuh severity and the anomaly score. Show a "baseline confidence" indicator on the dashboard.

**Improvement path (v2.0):** Confidence tiers (< 7 days / 7–30 days / 30+ days) surfaced explicitly; allow manual baseline seeding via the API from historical log archives.

---

### 2. High Dimensional Data (Isolation Forest)

**What it is:** Isolation Forest degrades with too many input features.

**Why it exists:** Wazuh alerts have 50+ fields; feeding all of them dilutes the signal.

**How to navigate it now:** Feature selection — only the ~10 fields listed in [anomaly.py](#anomalypy--anomaly-detection) are used.

**Improvement path (v2.0):** PCA as a preprocessing step, or an Autoencoder for higher-dimensional input; SHAP values to explain which features drove a given score.

---

### 3. LLM API Cost at Scale (cloud provider only)

**What it is:** Using a cloud provider costs money per summary, scaling with alert volume. This does not apply to the default local provider.

**Why it exists:** Cloud APIs charge per token.

**How to navigate it now:** The default `LLM_PROVIDER=ollama` avoids this entirely. If a cloud provider is chosen anyway, only summarise alerts above a threshold and cache summaries for near-duplicate alerts.

**Improvement path (v2.0):** Smart routing — low-severity alerts get a template summary, only high-severity ones reach a model at all, local or cloud.

---

### 4. No Feedback Loop (Anomaly Model Stays Static)

**What it is:** The Isolation Forest model is trained once and doesn't learn from analyst dismiss/escalate actions.

**Why it exists:** A proper feedback loop needs labelled-data management, a retraining pipeline, and model versioning — beyond PoC scope.

**How to navigate it now:** Analyst actions are logged to an `analyst-feedback-*` index even though nothing retrains on them yet — the labelled dataset is being built passively.

**Improvement path (v2.0):** Weekly retraining job pulling confirmed true/false positives from `analyst-feedback-*`; model versioning with rollback.

---

### 5. Local Model Quality vs Cloud Model Quality

**What it is:** A local 7B model (e.g. Mistral) produces noticeably lower-quality explanations than Claude or GPT-4-class models — occasionally vaguer or less precise about next steps.

**Why it exists:** Model size and training scale differences are real; this is an inherent trade-off of the local-by-default choice, not a bug.

**How to navigate it now:** The prompt template is deliberately explicit and structured to compensate — asking for specific fields (what happened, why suspicious, what's affected, what to consider) rather than an open-ended summary, which local models handle more reliably than free-form writing.

**Improvement path (v2.0):** Evaluate a security-domain-tuned local model if one becomes available; or expose a per-severity routing option where only the highest-confidence alerts optionally use a cloud provider, keeping the default fully local for everything else.

---

### 6. Single-Node OpenSearch (No HA)

**What it is:** Single node — if it goes down, alert storage and dashboard go down with it.

**Why it exists:** Sufficient for a PoC; a real cluster needs 3+ nodes and more hardware.

**How to navigate it now:** Acceptable for a test environment; enable periodic OpenSearch snapshots.

**Improvement path (v1.0 → production):** 3-node OpenSearch cluster with a master and two data nodes, provisioned via Terraform for production deployment.
